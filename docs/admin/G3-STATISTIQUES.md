# G.3 — Définition des statistiques Admin

Base : `7a6b67dc104e7cdb435981c7d7a5b825856d6051`. Lot local uniquement, aucun changement Prisma, rôle, permission ou prestataire. Le layout et les trois routes G.2 sont conservés.

## Contrat et sécurité

Nouveau `GET /api/v1/admin/statistics?from=YYYY-MM-DD&to=YYYY-MM-DD`. Les deux dates sont requises ; jours calendaires UTC, début inclus et fin exclue, 1 à 366 jours. Paramètres supplémentaires refusés. AdminGuard et permission existante `metrics/read` restent obligatoires. Aucun identifiant utilisateur, donnée de cours, réponse de diagnostic ou carte individuelle ne figure dans la réponse.

DTO portable `AdminStatistics` dans `packages/types`, schéma de période strict dans `packages/validation`, contrôle applicatif de permission, règles pures dans le domaine et agrégats PostgreSQL dans l'infrastructure. L'ancien endpoint metrics reste compatible.

Le formulaire conserve les dates en cours de saisie séparément de la période appliquée. Seul le bouton « Appliquer la période » soumet un intervalle valide à tous les agrégats et au journal ; il remet la pagination des événements en page 1. Le catalogue et le nombre actuel de comptes ne dépendent pas de la période. Les statistiques possèdent leur propre état de chargement/erreur et une reprise sans données périmées.

Les barres d'inscriptions sont accompagnées d'un titre, d'une description et d'un tableau accessible. Les répartitions d'abonnements incluent les valeurs textuelles et des éléments meter nommés. Les calculs monétaires d'affichage utilisent BigInt afin d'éviter les erreurs d'arrondi et pertes de précision. Seul l'EUR, devise du catalogue et des flux simulés/Stripe actuels, est divisé par 100. Le champ currency est libre : USD, JPY, KWD, codes inconnus ou absents ne sont pas automatiquement convertis. Par exemple, 700 USD stockés sont affichés comme « 700 unités stockées (échelle non vérifiée) USD », pas comme 7 USD.

## Test, simulation et réel

Le provider `mock` est classé SIMULATION. Tout autre provider est UNVERIFIED. Le schéma Payment ne conserve pas de marqueur test/live et le provider `stripe` ne suffit pas à le reconstruire. L'adaptateur Stripe actuel exige des clés de test ; cela ne prouve pas l'environnement de toutes les anciennes lignes ni de futurs imports.

L'interface indique explicitement « Non vérifiable (test/réel) » pour ces montants, sans les présenter comme revenus réels ou certifiés Stripe test. La configuration présente du processus n'est jamais utilisée pour requalifier des paiements historiques. Une distinction certifiée test/live demanderait une évolution de données approuvée séparément ; aucune migration anticipée ici. Les devises et statuts ne sont jamais fusionnés.

## Coût des lectures

Agrégation SQL côté base, aucune collection pédagogique chargée. Au plus 366 points temporels, et 200 groupes par tableau ; le 201e groupe déclenche une erreur explicite plutôt qu'un tableau tronqué. Comptages vérifiés dans l'intervalle sûr JavaScript ; les tokens, montants et estimations restent des chaînes exactes.

Transaction RepeatableRead : cohérence entre les quatre nouveaux agrégats. Délai d'attente transaction 3 s, limite globale 12 s et statement_timeout local 5 s. Un timeout renvoie une erreur, pas une fausse activité nulle. La période et la sortie sont bornées ; le nombre de lignes scannées dépend de la volumétrie et des index existants. User(createdAt) et certains agrégats peuvent nécessiter des index/rollups ultérieurement, avec autorisation de migration et mesures de charge. Aucun cache partagé de données Admin n'est ajouté. Le total global et l'ancien endpoint metrics sont des lectures distinctes : ils ne partagent pas le snapshot transactionnel de statistics.

## Revue des types PostgreSQL et des index

Lecture du catalogue de la base locale revynora_test : User.createdAt, AIUsage.createdAt, Payment.createdAt et UserSubscriptionHistory.startsAt sont timestamp without time zone, précision 3. Les createdAt ont CURRENT_TIMESTAMP comme valeur par défaut. La session locale auditée est UTC ; ce constat ne décrit pas le serveur de production, qui n'a pas été interrogé.

La convention est de stocker des valeurs calendaires UTC dans ces colonnes sans fuseau. Le test d'intégration force d'abord une session Pacific/Auckland et compare le résultat à celui obtenu en UTC, en vérifiant les événements exactement aux bornes. Il a révélé une conversion implicite des paramètres Date dépendante du fuseau de session. Le lecteur fixe désormais TimeZone=UTC via set_config(..., true) dans sa transaction, au même titre que statement_timeout. Aucun paramètre de rôle/base/serveur ne change ; aucune double conversion AT TIME ZONE n'est appliquée au timestamp sans fuseau. Cette correction ne peut pas reconstruire le fuseau d'anciennes valeurs qui auraient été stockées contrairement à la convention UTC. Les écritures utilisant CURRENT_TIMESTAMP supposent une session UTC, à vérifier lors d'un futur audit autorisé de production.

Index disponibles, confirmés localement et dans les migrations :

- User : clés primaires/uniques id, email, lower(email), stripeCustomerId ; aucun index commençant par createdAt.
- AIUsage : index (userId, createdAt), pas d'index temporel global dédié.
- Payment : index (userId, createdAt), unique providerReference ; pas d'index temporel global dédié.
- UserSubscriptionHistory : index (userId, startsAt, endsAt) et unique (providerSubscriptionId, startsAt, subscriptionId), pas d'index commençant par startsAt.
- Subscription : clé primaire id utilisée pour la jointure, unique code.

Les agrégats globaux ne filtrent pas userId : les index composites ne garantissent donc pas une lecture sélective par période. EXPLAIN sans ANALYZE sur la petite base locale prévoit des Seq Scan pour les quatre tables de faits, avec Index Scan sur Subscription_pkey pour la jointure. Ce sont des plans estimés, pas une mesure de charge ni une projection de performance production. LIMIT 201 borne la sortie, pas le travail du GROUP BY ou le volume scanné.

Le délai de 5 s est par instruction ; 12 s est le budget d'exécution de la transaction interactive Prisma, auquel peut s'ajouter l'attente de connexion de 3 s et le traitement HTTP. Ces réglages ne garantissent pas un temps de réponse HTTP strict de 12 s, ni une protection contre une accumulation de requêtes Admin concurrentes. L'ancien endpoint metrics conserve ses propres agrégats, sans nouvelles limites ajoutées par ce lot. Prévoir des mesures représentatives et, si nécessaire, index temporels, rollups, contrôle de concurrence ou cache après validation séparée. Aucune migration ou index créé ici.
